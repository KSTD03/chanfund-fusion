## 1. 背景

基于 500 只股票 × 6年（2019-2026）回测的实际运行数据：

| 指标 | 数值 |
|------|------|
| 股票数 | 500 只 |
| 交易日 | 1531 天 |
| 内存峰值 | 0.88 GB |
| 运行时间 | 194 秒 |
| 数据格式 | Parquet（压缩比 28.3%） |

**线性推算 4441 只：**
- 预期内存峰值：0.88 × (4441/500) × 1.2（信号引擎溢出因子）= **~8.4 GB**
- 预期运行时间：194 × (4441/500) × 1.1（调度开销）= **~28 分钟**
- 服务器可用内存：8GB（预留 2GB 给操作系统，实际可用 ~6GB）

**结论：** 全量回测预估 8.4GB > 6GB 可用上限，需要优化内存策略。

## 2. 数据加载策略

### 2.1 方案 A：分批次加载（推荐）

**原理：** 按股票批次加载，每批处理完后释放数据，保障内存峰值可控。

```
批次1: 0-500股 → 预热 → 回测 → 释放数据
批次2: 501-1000股 → 预热 → 回测 → 释放数据
...
批次N: 最后一小批 → 完成
```

**关键设计：**

- **批次大小**：500 只/批（经验证 0.88GB，预留余量）
- **信号引擎状态缓存**：`tech_engine.chan_cache` 必须跨批次保留（因为信号需要完整历史结构）
- **持仓状态**：全局共享（不受批次影响）
- **每日迭代**：所有批次在同一天内依次处理，然后进入下一天

**内存估算：**

| 模块 | 500只 | 4441只(单批) | 4441只(9批) |
|------|-------|-------------|-------------|
| 行情数据 (Data dict) | 523 MB | 4.6 GB | 523 MB × 9批 = 峰值 523 MB |
| 缠论结构 (chan_cache) | 350 MB | 3.1 GB | 3.1 GB（不清除） |
| 信号队列+日志 | 7 MB | 62 MB | 62 MB |
| **总计** | **880 MB** | **~7.8 GB** | **~3.7 GB** |

**结论：** 分批次后内存峰值从 8.4GB 降至 3.7GB，8GB 服务器完全可行。

### 2.2 方案 B：内存映射（备用）

- 使用 `numpy.memmap` 或 `pandas.HDFStore` 将行情数据映射到磁盘
- 优点：不占用 RAM
- 缺点：读取速度依赖磁盘 I/O，回测速度可能降低 3-5 倍
- 适用场景：方案 A 仍然超限时的后备方案

### 2.3 推荐策略

**采用方案 A（分批次加载），批次大小 500，共 9 批。**

如果需要进一步降低内存：

1. 将 chan_cache 中无效的缠论状态定期清理（如超过 60 天无信号的股票）
2. 将交易日志改为流式写入磁盘（不保留在内存中）

## 3. 中间数据缓存策略

| 数据模块 | 是否常驻 | 原因 | 估算大小 |
|----------|---------|------|---------|
| **chan_cache**（缠论结构状态） | ✅ 必须常驻 | 信号引擎依赖历史结构判断信号 | 3.1 GB |
| **Data dict**（行情的转置索引） | ❌ 批次后释放 | 每批处理完即可回收 | 523 MB/批 |
| **信号队列**（当日信号） | ❌ 日末释放 | 每日生成，日末清空 | < 1 MB |
| **持仓状态** | ✅ 必须常驻 | 跨批次共享 | < 1 MB |
| **交易日志** | ❌ 流式写入磁盘 | 减少内存占用 | 可调（当前~15MB） |
| **财务数据缓存** | ✅ 必须常驻 | 每日查询需要 | < 50 MB |
| **成交量缓存** | ✅ 必须常驻 | 均量计算需要 | < 50 MB |

**优化策略：**

1. **chan_cache**：执行定期 GC（每 30 天清理一次无信号的股票）
2. **交易日志**：改为 CSV 流式追加写入，`trade_log` 列表改为 `List[dict]` 只在内存中保留最近 100 条
3. **Data dict**：每个批次开始时加载，结束时 `del data; gc.collect()`

## 5. 执行时间预估

基于 500 只回测耗时 194 秒（3.2 分钟）的实际数据：

| 阶段 | 500只实测 | 4441只估算 | 说明 |
|------|----------|-----------|------|
| 数据加载 | 16 s | 52 s | 9批 × ~6s 加载 + 合并 |
| 预热 | 48 s | 182 s | O(n)，但有优化空间（并行） |
| 回测主循环 | 125 s | 1,025 s | O(n×T)，每日循环1531天 |
| 报告生成 | 5 s | 15 s | 固定费用 |
| **总计** | **194 s** | **~1,274 s** | **~21 分钟** |

**优化潜力：**
- 预热并行化（multi-processing）：可减少 40-50%
- 信号引擎增量更新：从 Python 改为 C 扩展或 numba JIT：可减少 30-40%
- **预计优化后全量可压缩至 12-15 分钟**

## 6. 实施计划

### 6.1 代码修改

在 `run_chanfund_v20_backtest.py` 基础上添加批次处理模式：

```python
def run_backtest_batched(
    data_dir: str,
    all_stocks: List[str],
    batch_size: int = 500,
    ...  # 其他参数同 run_backtest
):
    # 获取交易日历
    all_dates = get_trade_calendar(...)
    
    # 分批次处理
    for batch_i in range(0, len(all_stocks), batch_size):
        batch = all_stocks[batch_i:batch_i + batch_size]
        data = load_daily_csv_data(data_dir, specific_stocks=batch)
        
        # 批次内的回测（共享 chan_cache + positions）
        run_backtest_batch(data, batch, ...)
        
        # 批次结束释放
        del data
        gc.collect()
```

## 7. 风险与备选

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| 内存超 6GB | 中 | 高（OOM） | 缩小批次到 300；启用 memmap 备用 |
| 回测时间超 1 小时 | 低 | 中 | 启动并行预热；使用 JIT 加速 |
| 批次间数据不一致 | 低 | 高（结果错误） | 每日日志校验，离线对账 |
| chan_cache 跨批次增长失控 | 中 | 中 | 定期 GC；限制最大缓存数量 |
